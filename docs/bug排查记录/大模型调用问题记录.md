## 2026-09-26 大模型返回内容无法解析为 JSON（DeepSeek-V4-Pro · 总结摘要）

### 问题现象

- 复现链路：前端解析 B 站视频 `BV1q47f66ERF`，模型选择 **DeepSeek-V4-Pro**（`deepseek-v4-pro`）。
- 「总结摘要」页签报错：

  ```text
  大模型返回内容无法解析为 JSON： Expecting ',' delimiter: line 28 column 6 (char 1063)
  ```

- 报错来源：`backend/ai/summary.py` 总结链路中 `json.loads` 抛出的
  `json.JSONDecodeError` 信息被包装后抛给前端（思维导图链路同构，存在同类风险）。

### 根因分析

1. **直接原因——模型偶发输出非法 JSON**：
   - `Expecting ',' delimiter` 的语义是：交给 `json.loads` 的文本不是合法 JSON，
     解析器在第 28 行第 6 列（char 1063，落在 `chapters` 数组区域）期望一个逗号。
   - 典型诱因：成员间漏逗号（`{"a":1 "b":2}`）、尾随逗号、字符串值内未转义的英文
     双引号、JSON 前后夹带含花括号的推理/杂文本。
2. **放大因素——旧提取器无修复能力**：
   - 旧 `_extract_json` 仅「代码围栏 → 全文 → 首 `{` 到尾 `}`」三级退化。
   - 模型一旦在 JSON 前后夹带含花括号的推理文本，「首 `{` 到尾 `}`」切片必然跨越
     杂文本而非法；漏逗号一类缺陷则三级全部失败。
   - 于是**一次可修复的偶发瑕疵被直接放大成用户可见错误**。
3. **可观测性盲区——无证据留痕**：
   - 旧代码抛错时丢弃模型原始输出，也不记录 `finish_reason` / `usage`，事后无法
     区分「截断 / 散文 / 夹带杂文本 / 漏逗号」等缺陷类型。
   - `max_tokens=2048` 对结构化长 JSON 偏小，截断（`finish_reason=length`）本身
     也是潜在诱因之一。
4. **偶发性确认（定性关键）**：
   - 从数据库取该视频缓存字幕，以**生产同路径**（相同 messages 调
     `deepseek-v4-pro`）复现，**本次返回合法 JSON**——证明属模型偶发输出瑕疵，
     而非确定性 Bug。
   - 因此正确的修复方向是**服务端容错消化**，而非仅调整提示词碰运气。

### 排查过程

1. 读 `backend/ai/summary.py`、`backend/ai/llm.py`：明确解析链路与报错触发条件
   （三级退化全失败才抛错），确认旧提取器无任何修复手段。
2. 读 `backend/main.py`、`backend/ai/config.py`：确认生产路径为
   `ai_config.load_config(provider, model)` 按用户所选模型解析 cfg，总结接口以
   `summarize(..., cfg=cfg)` 传入。
3. 写临时复现脚本：从数据库取该视频缓存字幕（2011 字符）→ 用与 summary 完全相同
   的 messages 调 `deepseek-v4-pro` → 打印原始输出与 char 1063 附近缺陷窗口 →
   本次 `EXTRACT: OK`，确认偶发性与缺陷窗口位置（chapters 区）。
4. 结论：为提取器补「多候选提取 + 本地修复 + 模型重试」三级容错，并补齐证据留痕。

### 解决方案

1. **新增共享模块 `backend/ai/jsonx.py`**（总结 / 思维导图共用），三级递进：
   - **多候选提取**：代码围栏 → 全文 → 字符串感知的顶层平衡 `{...}` / `[...]`
     片段（容错夹带杂文本/推理）→ 首 `{` 到尾 `}`；
   - **本地轻修复** `repair_json`：状态机补漏逗号、去尾随逗号（字符串感知，**绝不
     改动字符串内容**）；串内未转义双引号等歧义缺陷不做猜测性修复；
   - **模型修复重试** `chat_json`：首次解析失败时把坏输出原样作为 assistant 消息
     回传，附修复指令要求只输出修复后的合法 JSON（`temperature=0`），仅失败时触发；
   - 首次失败留痕 log warning（含 `finish_reason` 与 raw 前 300 字符），补齐盲区。
   - 补充说明: 「总结摘要 / 思维导图」报错是因为：大模型在自由文本里输出一段 JSON，
   于是这段 JSON 可能漏逗号、夹带推理杂文本、被 max_tokens 拦腰截断——jsonx 三级
   容错（多候选提取→本地修复→模型重试）专门治这类问题
2. **`backend/ai/llm.py` 新增 `chat_meta`**：返回 `{content, finish_reason, usage}`，
   `finish_reason=length` 即截断的直接证据；`chat` 改为便捷封装，既有调用方不受影响。
3. **`backend/ai/summary.py` / `backend/ai/mindmap.py` 切换 `jsonx.chat_json`**：
   - `max_tokens` 由 2048 提至 4096，为结构化长 JSON 留余量、防拦腰截断；
   - 提示词新增第 4 条规则：字符串值内引用一律用中文引号「」，禁止未转义英文双引号
     与反斜杠，禁止漏逗号或尾随逗号；
   - `PROMPT_VERSION` v1 → v2，旧缓存随缓存键（含版本号）自然失效。
4. **测试同步**：
   - 新增 `tests/test_ai_jsonx.py`：多候选提取、本地修复（含「字符串内容逐字不改」
     约束）、首次成功仅单次调用、修复重试消息结构（坏输出原样回传 + 修复指令）4 用例；
   - `tests/test_ai_mindmap_qa.py` 的 `_patch_chat` 改为同时 patch `llm.chat` 与
     `llm.chat_meta`（新链路走 `chat_meta`，qa 仍走 `chat`）；
   - 两个测试文件对旧 `_extract_json` 的引用统一改为 `jsonx.extract_json` /
     `jsonx.JSONExtractError`。

### 验证结果

- 离线回归：`test_ai_jsonx` + `test_transcribe_ai` 共 **19 passed**；
  `test_storage_cache` + `test_ai_mindmap_qa` 共 **20 passed**；`test_smoke`
  （全应用导入链）通过。
- 真实链路复验：取该视频缓存字幕走 `summarize(refresh=True)`（`deepseek-v4-pro`）
  → 成功生成总结（8 条要点、5 个章节、8 个关键词）并写入 v2 缓存；用户重开页面时
  「总结摘要」页签直接命中缓存正常渲染。
- 此后偶发瑕疵再出现时会被服务端两级消化（本地修复 → 模型重试）；仅当两级均失败才
  向用户报错，且日志已含 `finish_reason` 与 raw 头部证据，可直接定性。

### 关键收获

- LLM 结构化输出必须假设「偶发非法 JSON」：提取器容错三级（多候选 → 本地修复 →
  模型重试）是标配；提示词约束只能降低概率、不能消除。
- 解析失败抛错时务必保留 raw 与 `finish_reason`，否则事后无法定性缺陷类型
  （与项目「AI 服务层错误处理与可观测性通用规范」一致）。
- `max_tokens` 要为结构化输出预留余量；截断是 JSON 被拦腰切断的高频根因。
- 提示词变更必须 bump `PROMPT_VERSION`，借缓存键自然失效，避免旧缓存掩盖新逻辑。
