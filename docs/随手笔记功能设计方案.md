## 1. 竞品功能拆解（结论先行）

竞品截图（随手笔记 Tab）拆出的能力原子，共 7 条：

| # | 竞品能力 | 本质 | 对我们的必要性 |
|---|---|---|---|
| 1 | 笔记作为结果页第 N 个 Tab，与总结/字幕/导图/评论/问答并列 | 笔记的上下文是「这一个视频」 | 必须，直接复用我们的 Tab 体系 |
| 2 | 插入时间戳（`Ctrl+Shift+T`） | 编辑器 ↔ 播放器 currentTime 的单点桥接 | 必须，是我们已有的 `playerCtrl.getTime()` 能力 |
| 3 | 复制时间戳（`Ctrl+Alt+T`） | 跨应用粘贴（记到别处） | 低成本，顺带做 |
| 4 | 插入当前截图（`Ctrl+Shift+S`） | 抓当前帧 → 落库 → 内联插图 | 必须，但**我们是 B 站/YouTube iframe + 抖音流播三种播放器混合**，抓取难度高于竞品，是方案最大技术点（见 §6） |
| 5 | 自动保存，无需手动提交 | 编辑体验（防丢） | 必须，需带并发冲突保护 |
| 6 | 富文本工具栏（加粗/列表/任务/代码/链接/图片/表格/Block type） | 记录结构化内容 | 降级为「Markdown 子集」，理由见 §6.3 |
| 7 | 顶部「添加合集 / 章节(7) / 复制 / 下载 / 导出 / 分享」 | 笔记汇入合集与导出 | 合集我们已有（`collections`），导出做 Markdown；分享（公开链接）本期不做（涉及权限模型） |

**竞品没做、但我们有独特优势可做的**（差异化）：
- 我们已有**带时间戳的字幕文本**（`Transcripts.segments`）与 **AI 章节时间线**（`mindmap` 的分支）。竞品要自己识别章节，我们直接是现成的 → 笔记可以「一键引用字幕句 / 一键引用章节」，把笔记从"手抄"升级为"摘取 + 批注"。
- 我们已有 **AI 问答会话**（`QaSession`）。笔记与问答同源，可把一条 AI 回答直接转正为笔记（`source_type=qa`）。
- 我们已有 **全局内容缓存 + 用户历史**（`content_key` 机制）。笔记天然可按 `content_key` 归属到视频，跨设备、跨链接形式（B 站长链/短链）都能对齐。

## 2. 产品定位与分期

**一句话定位**：看视频时，把灵感/重点/疑问**带时间戳、带画面**地记下来，之后能按时间线回看、一键跳播、导出成 Markdown。

| 阶段 | 范围 | 交付判据 |
|---|---|---|
| **P0（本迭代）** | 笔记表 + `/api/me/notes` CRUD + 结果页第 6 个 Tab + 自动保存 + 时间戳插入/点击跳播 + 图片粘贴上传 + **原生播放器前端抓帧**（抖音等） | 单视频可记录 ≥50 条笔记，刷新/换设备不丢；时间戳 chip 点击跳播；贴图可回看 |
| **P1** | 后端 ffmpeg 抽帧兜底（B 站/YouTube）、笔记时间线面板、按视频聚合的「我的笔记库」页、Markdown 导出、标签/收藏、历史 `kinds` 加 `note` 徽标 | 三平台截图能力一致；可从侧边栏进入笔记库统一浏览 |
| **P2** | AI 能力：一键生成笔记初稿（总结要点转为带时间戳笔记）、笔记润色/打标、闪记卡（笔记→复习卡片）、合集级笔记汇总报告 | 与套餐权益/用量计量（`usage_counters`）联动 |

**非目标（明确不做）**：协同编辑、公开分享链接、块级无限画布编辑器、移动端原生手势白板。

## 3. 总体架构

沿用既有分层，**新增 `backend/notes/` 能力包**（与 `library/` 同级同风格），不改 `library` 既有职责边界：

```
backend/notes/
  __init__.py      # 门面导出：router / notes_error_handler / 供 main.py include_router
  models.py        # ORM：UserNote / NoteImage（放 storage/models.py 里更符合现状 → 实际落位见 §4）
  store.py         # 仓储：首参一律 user_id（复刻 library/store.py 的「隔离落在签名层」）
  service.py       # 编排：上限滚动、级联、自动保存冲突、图片归属
  frames.py        # 抽帧：前端抓帧的兜底通道（ffmpeg -ss 取帧，无 ffmpeg 回退封面）
  images.py        # 图片落盘：魔数校验（复用 auth/avatar.py 的 sniff_image 思路）
  config.py        # 上限：NOTE_MAX_CHARS / NOTES_MAX_PER_VIDEO / NOTE_IMAGE_MAX_BYTES …
  errors.py        # NotFoundError / ValidationError / CapExceededError / ConflictError(409)
  router.py        # /api/me/notes/*，一律 Depends(require_user)
```

`main.py` 注册（与 auth/library 同风格）：

```python
from backend import notes
app.add_exception_handler(notes.NotesError, notes.notes_error_handler)
app.include_router(notes.router)
```

**为什么不塞进 `library/`**：library 的语义是「归属与时间线」（历史/合集/会话），
笔记是**内容本体**（要存正文、图片、版本、冲突），职责与上限策略完全不同；
混进去会让 `library/store.py`（已 511 行）继续膨胀。
两者只共享一条约定：`user_id` 列级隔离 + `content_key` 视频身份键。

## 4. 数据模型

### 4.1 `user_notes`（笔记本体）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | String(32) PK | uuid4 hex |
| `user_id` | String(32) index | 归属用户（列级隔离） |
| `content_key` | String(64) index | 视频身份键 = `transcript_key(url)`，与 `UserHistory.content_key` 同一算法（跨链接形式对齐） |
| `url` / `title` | Text | 视频链接与标题**快照**（全局缓存过期后笔记仍可读，同 `UserHistory` 语义） |
| `body` | Text | Markdown 源文（**唯一事实源**，渲染由前端完成），上限 `NOTE_MAX_CHARS`（默认 20000） |
| `marks` | JSONCol | 时间戳索引数组 `[{"t":192.5,"label":"03:12"}]`，写库时由服务端从 body 解析生成（不信任客户端），供时间线聚合与导出，免每次全文正则 |
| `tag` | String(16) | 语义标签：`blank`（空）/ `key` 重点 / `question` 疑问 / `idea` 灵感（P1 用，P0 建列预留） |
| `starred` | Boolean default False | 收藏（P1 过滤用，P0 建列预留） |
| `source_type` | String(16) default `manual` | `manual` / `subtitle`（引用字幕句）/ `chapter`（引用章节）/ `qa`（AI 回答转正）/ `ai_draft`（P2） |
| `source_ref` | String(64) default "" | 引用来源锚点（如 `qa_messages.id`），仅溯源展示，不做外键 |
| `image_count` | Integer default 0 | 冗余计数（列表卡片显示"含 3 张图"，避免 join） |
| `created_at` / `updated_at` | DateTime(tz) | `updated_at` 兼作**自动保存冲突基线**与列表排序键 |

约束与索引：
- `Index("ix_user_notes_user_updated", "user_id", "updated_at")` — 笔记库列表倒序；
- `Index("ix_user_notes_user_content", "user_id", "content_key")` — 结果页取该视频全部笔记；
- 一个视频**允许多条笔记**（对齐竞品：一个 Tab 内是一篇一篇文章）。竞品是「每视频一篇长文」，我们是「每视频多篇 + 可按时间线合并导出」，理由：多轮学习会产生离散灵感，单篇长文会让自动保存的冲突面变大、也不便按时间戳聚合。P1 提供「合并为一篇」动作。

### 4.2 `note_images`（笔记图片）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | String(32) PK | uuid4 hex，**同时是文件名**（防路径穿越：写库前校验 `^[0-9a-f]{32}$`） |
| `user_id` | String(32) index | 归属用户（图片是私有资源，读取需鉴权） |
| `note_id` | String(32) index nullable | 归属笔记；**上传先于笔记存在**（新建未保存时贴图）→ 可空，由 service 在保存时认领 |
| `content_key` | String(64) default "" | 视频身份键，便于孤儿清扫与按视频统计 |
| `t` | Float nullable | 截图对应的视频时间点（秒）；非截图（用户贴图）为 NULL |
| `mime` | String(32) | 由**魔数**判定，不信 Content-Type |
| `bytes` | Integer | 体积，用于配额与清扫 |
| `created_at` | DateTime(tz) | 孤儿判定依据 |

**为什么图片走 DB + 磁盘，而不是 base64 塞进 body**：base64 会让正文膨胀 ~33%，把 `body` 撑大后每次自动保存都全量重写、列表接口也拖泥带水，且无法做「按视频清理/配额」。

落盘：`data/note_images/{id}.{ext}`（目录由 `NOTE_IMAGE_DIR` 覆盖，与 `AVATAR_DIR` 同一解析规则）。读端点：`GET /api/me/notes/images/{id}` → `Response(content, media_type=mime, headers={"Cache-Control": "private, max-age=31536000, immutable"})`（id 即内容指纹，天然 immutable）。

### 4.3 存储层三条既有规范必须遵守

1. **JSON 列方言抽象**：`marks` 一律用 `models.py` 里的 `JSONCol = JSON().with_variant(JSONB, "postgresql")`，不得硬编码 `JSON`（否则 PG 上拿不到 JSONB 优势）。
2. **声明式迁移**：新表由 `Base.metadata.create_all` 自动建（只建缺失表），**无需**改 `migrations.py`；但若后续给 `user_notes` 加 NOT NULL 无默认值的列，必须同时给 `server_default`，否则 `ALTER TABLE ADD COLUMN` 在 SQLite 直接失败。
3. **代理主键 + 业务唯一键**分离的既有风格：本表无跨用户业务键，故 `id` 单主键即可，不引入 `(kind,key)` 式唯一约束。

### 4.4 历史 kinds 联动

`library.service.KINDS` 增加 `"note"`，`core.js` 的 `KIND_META` 增加：

```js
note: { short: '记', full: '随手笔记', cls: 'bg-cyan-50 text-cyan-600' },
```

→ 侧边栏/历史列表/搜索联想的徽标**零改动自动生效**（它们都读 `kindBadges`）。写入时机：创建笔记时 `record_action(user_id, url, title, "note", source)`；删除该视频最后一条笔记时 `history_remove_kind(user_id, content_key, "note")`（与 `_sync_qa_kind` 同一套做法）。

## 5. API 契约

全部挂 `/api/me/notes`，**一律 `Depends(require_user)`，不看 `AUTH_ENABLED` 灰度开关**（与 `library/router.py` 同一约定：私有资源永远要求登录）。异常语义 → HTTP：`NotFound 404 / Validation 400 / CapExceeded 400 / Conflict 409`。

| 方法 | 路径 | 请求 | 响应 | 说明 |
|---|---|---|---|---|
| GET | `/api/me/notes?content_key=&q=&tag=&starred=&limit=&offset=` | — | `{items:[…], total}` | 列表（`updated_at` 倒序）；`content_key` 留空=笔记库全量 |
| POST | `/api/me/notes` | `{content_key, url?, title?, body, tag?, source_type?, source_ref?}` | `201 {note}` | 新建；`body` 截断至上限；解析 `marks` |
| GET | `/api/me/notes/{id}` | — | `{note, images:[…]}` | 详情（含图片元数据，供渲染） |
| PATCH | `/api/me/notes/{id}` | `{body?, title?, tag?, starred?, base_updated_at?}` | `{note}` \| `409` | **自动保存主通道**，见下 |
| DELETE | `/api/me/notes/{id}` | — | `{ok:true}` | 级联删该笔记的图片行与磁盘文件 |
| POST | `/api/me/notes/images` | multipart：`file`，form：`note_id?`、`content_key`、`t?` | `201 {image:{id,url,t,mime,bytes}}` | 传图（截图/贴图共用）；返回 `url` 可直接进 `<img src>` |
| DELETE | `/api/me/notes/images/{id}` | — | `{ok:true}` | 删图（编辑器删图时调用） |
| POST | `/api/me/notes/frames` | `{url, t, fast?:bool}` | `{image:{…}}` | **后端抽帧兜底**（P1）：`fast=true` 只用已有流播缓存，缓存无 → 404 提示 |
| GET | `/api/me/notes/export?content_key=` | — | `text/markdown` 附件 | 按 `marks` 时间序合并该视频全部笔记（P1） |

### 5.1 自动保存的冲突保护（必须设计，不能省）

`.env` 里 `SESSION_TTL_HOURS=168`，用户可能开两个标签页编辑同一视频笔记 → 后写覆盖前写是真实风险。约定：

- 前端每次 PATCH 带 `base_updated_at`（自己上次拿到/写回的 `updated_at`）；
- 服务端比较：库中 `updated_at > base_updated_at` → 返回 `409 {detail:"该笔记已在其他窗口被修改", server:{…}}`；
- 前端收到 409：不静默覆盖，弹一条内联提示「内容有更新，[加载服务端版本] / [以我的版本覆盖]」，覆盖即不带 `base_updated_at` 重试（显式放弃冲突检测）。
- `base_updated_at` 缺省（老客户端/脚本）→ 跳过检测，保持向后兼容。

### 5.2 上限与配额（env 驱动，与 `library/config.py` 同范式）

```python
NOTE_MAX_CHARS        = 20_000   # 正文（服务端截断，不报错：笔记容忍截断比拒绝提交更友好，但返回 note.truncated=true 供前端提示）
NOTES_MAX_PER_USER    = 500      # 每用户笔记数，超限滚动淘汰最旧不活跃（同 history/qa 语义）
NOTE_IMAGES_MAX_PER_NOTE = 30    # 单笔记图片数
NOTE_IMAGE_MAX_BYTES  = 5MB      # 单图（截图 PNG 通常 300KB~1.5MB）
NOTE_IMAGE_TOTAL_MAX_BYTES = 500MB  # 每用户图片总量，超限 400 提示清理
```

## 6. 前端设计（本方案技术难点集中处）

### 6.1 挂载为第 6 个 Tab：三处必须同步改

现有 Tab 是数据驱动的，加一个 Tab 只需改常量 + 一个 loader，**但有两个隐藏约束**：

1. `TAB_ORDER` 加 `'notes'`、`TAB_LABELS`/`TAB_ICONS` 各加一项 → `panelHtml` 自动多出一个 tabpanel 与按钮（`renderCard` 无需改）。
2. `TAB_LOADERS` 的签名是 `(url, panel)`，而笔记需要 `content_key`、`card` 与播放器 → **统一改为 `(url, panel, card)`**（5 个既有 loader 忽略第三参即可），`switchTab`/`prefetchTab` 调用点各传一次 `card`。这是最小改动面，避免为 notes 单开一条渲染路径。
3. `runAllAi`（一键 AI 分析）**不要**预取 notes：笔记是用户内容，不该被"分析"按钮触发加载；同时 notes 在批量 compact 卡里**不提供**（`renderCard` 的 compact 分支过滤掉该 Tab），因为 compact 卡没有共享左栏播放器（`playerCtrl` 单例与卡片绑定），时间戳/截图语义无处安放。

> 关键约束：`playerCtrl` 是**模块级单例**（`result.js` L25），换卡即 `setPlayerCtrl(null)` 销毁。笔记 Tab 必须通过 `onPlayer(fn)` 订阅，而不是在 loader 里一次性读 `playerCtrl`——否则会出现「先开笔记 Tab、后点封面播放 → 按钮永远置灰」。

### 6.2 时间戳：编辑器 ↔ 播放器双向桥接

- **插入**（`Ctrl+Shift+T` / 工具栏按钮）：读 `playerCtrl.getTime()`；`null`（B 站外链播放器无回读）→ 回退到「从字幕 Tab 当前高亮行取 `data-start`」，仍无则提示「请先点击播放器的播放/暂停，或用字幕行时间戳」；取到值则在光标处插入 `␞03:12␟` 内部标记，渲染为蓝色 chip。
- **点击 chip 跳播**：`playerCtrl ? playerCtrl.seek(t) : mountLeftPlayer(t)` —— 与字幕行点击完全同一策略（复用 L37-72 的挂载逻辑，不重复实现）。
- **解析格式**：`body` 里时间戳以 `@[mm:ss](t=192)` 形式的 Markdown 内联链接存储（**人类可读、导出 Markdown 天然带时间、正则易解析**），前端渲染时转 chip。服务端 `marks` 由该正则提取，不依赖客户端上报。
- **复制时间戳**（`Ctrl+Alt+T`）：`copyText(fmtTs(t))`，复用 `core.js` 的 `copyText`（含非安全上下文回退）。

### 6.3 编辑器选型：为什么不上富文本 / Block 编辑器

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. `contenteditable` 自研富文本 | 与竞品观感一致 | 序列化/粘贴清洗/XSS 面极大；无构建工具下自己写等于踩坑 | ❌ |
| B. CDN 引入 TipTap / Editor.js | 功能全 | 与「零构建 + 无第三方库」现状冲突（导图 SVG、字幕导出都是手写的）；体积与版本漂移；导出格式受制于库 | ❌（P2 再评估） |
| **C. Markdown 源文 + 轻工具栏 + 双模式（编辑/预览）** | 事实源是纯文本（可导出、可 diff、可 AI 处理）、XSS 面小（渲染时全量 `escapeHtml` 后仅白名单替换）、与现有代码风格一致 | 非所见即所得 | ✅ **采用** |

C 的落地细节：
- 默认**编辑态**为 `textarea`（自动增高，`scroll` 不外溢到 Tab），工具栏按钮对选区做 Markdown 包裹（`**b**`、`_i_`、`` `c` ``、`- `、`1. `、`- [ ] `、`> `、表格模板）；
- **预览态**渲染 Markdown 子集：标题/加粗/斜体/删除线/行内码/代码块/有序无序/任务/引用/链接/图片/表格；实现沿用 `result.js` 里已有的 `highlight()`（先 `escapeHtml` 再替换）思路，**不接受任何原始 HTML**；
- 时间戳 chip 与图片是两种白名单扩展语法，渲染成 `<button class="note-ts">` 与 `<img>`；
- 单视频笔记数 >1 时，Tab 内是「笔记卡片流 + 新建按钮」，卡片默认折叠显示预览摘要，点开进编辑态（对齐竞品"一篇文章"心智，同时保留多篇能力）。

### 6.4 截图：三平台三通道，能力矩阵先行

这是与竞品体验差距最大、也最容易设计错的地方。我们的播放器有三种形态（见 `player.js` 注释）：

| 平台 | 播放器形态 | 能否前端 canvas 抓帧 | 采用通道 |
|---|---|---|---|
| 抖音等（无外链播放器） | `mountNative`：同源 `/api/stream` + `<video>` | ✅ **可以**（同源，无 taint） | **前端 `canvas.drawImage(video, …)` → `toBlob('image/png')` → 上传**（P0，最快、零服务端负载） |
| YouTube | IFrame API 跨域 iframe | ❌（跨域 taint，`toDataURL` 抛 SecurityError） | 前端插 `poster` 帧占位 + 提示；P1 走后端 `POST /api/me/notes/frames`（`ffmpeg -ss` 从流播缓存取帧） |
| B 站 | `player.bilibili.com` 跨域 iframe | ❌ | 同上 |

实现要点：
- `playerCtrl.platform === 'native'` 且 `ctrl.el` 存在 → 前端抓帧；否则按钮显示为「插入截图（后端取帧）」，走 frames 端点；两者都不可用时降级为「插入封面图」（用 `info.thumbnail` 走贴图通道，永远可用，保证不出现死按钮）；
- 抓帧前**先 `video.pause()`**，抓完恢复（避免连续帧与音频空转）；`canvas` 尺寸取 `videoWidth/videoHeight`，长边 >1920 时等比缩到 1920（体积可控）；
- 竞品的 `Ctrl+Shift+S` 是浏览器/系统高频占用组合（Chrome 部分版本、输入法），我们保留按钮为主、快捷键为辅，并在 `title` 里写清；
- 后端 `frames.py`：`ffmpeg -ss {t} -i {cached_file} -frames:v 1 -q:v 3 out.jpg`；缓存文件复用 `main.py` 的 `_stream_file(url)`（`fast=true` 时只查 `_stream_cache` 命中，不触发整片下载——**这一点很关键**，否则 B 站长视频抽一帧会卡住几十秒，踩既有「同步阻塞 + 线程池长任务占用」的坑）；无 ffmpeg → 回退 yt-dlp `thumbnail`（封面，非当前帧，返回 `frame_type:"poster"` 让前端标注「封面帧」）。

### 6.5 自动保存与状态机

```
[草稿] --输入 800ms 防抖 / 失焦 / 切 Tab / 关页(beforeunload 用 sendBeacon)--> [保存中] --ok--> [已保存 hh:mm:ss]
                                                                              --409--> [冲突：内联二选一]

```

- 视图状态挂在 `card._noteState`（与 `card._aiState` 同一位置约定），换卡自然销毁。

## 8. 安全与边界（逐条对应既有踩坑）

1. **XSS**：`body` 永不渲染原始 HTML —— 先 `escapeHtml` 再按白名单替换（沿用 `result.js` 的 `highlight()` 模式）；图片 `src` 只允许本站 `/api/me/notes/images/…` 与 `http(s)` 外链，`onerror` 降级为占位；`javascript:` 一律拒绝（对齐 `User.website` 的既有防注入策略）。
2. **上传格式**：按**魔数**判定真实格式，只收位图（JPG/PNG/GIF/WEBP），**明确拒绝 SVG**（可内嵌脚本，`auth/avatar.py` 已确立此规范）；`_read_upload` 按块读、超限即止，防大文件吃内存。
3. **路径穿越**：图片文件名 = `note_images.id`（uuid4 hex），写/读前正则校验 `^[0-9a-f]{32}$`；`id` 来自 DB 也照样校验（与 `avatar._check_id` 同一"纯防御"口径）。
4. **IDOR / 越权**：所有 store 函数首参强制 `user_id`（漏传即 TypeError），查询一律带 `user_id` 过滤；跨用户访问统一 `404`（不确认资源存在），与 `library` 完全一致。
5. **SSRF（重要）**：`POST /api/me/notes/frames` 接收 `url` 并交给服务端下载器/ffmpeg —— 这是我们既有 SSRF 风险面上**新增的一个入口**。必须：① 复用 `downloader` 既有的 URL 白名单/协议校验（仅 http/https、拒绝内网与本机地址、拒绝重定向到内网）；② `t` 限定 `0 ≤ t ≤ 24h`；③ 该端点走 `_AUTH_GATE`（需登录）并纳入 IP 级限流（对齐 `throttle` 范式）。
6. **长任务阻塞**：抽帧不得在事件循环里 `subprocess.run` 长等 —— `frames.py` 用 `Popen` + `timeout`（对齐 `_FFMPEG_TIMEOUT`），端点声明为同步 `def`（Starlette 线程池），且 `fast=true` 优先，避免整片下载占满线程池（既有明确瓶颈教训）。
7. **磁盘膨胀**：孤儿图片（`note_id IS NULL` 且 `created_at` 超 24h）与删笔记残留文件必须清扫 —— 在 `service` 的写路径上做**惰性清扫**（每用户每次写入时按 `NOTE_IMAGE_TOTAL_MAX_BYTES` 与 TTL 淘汰最旧），并暴露 `notes_orphan_images` 计数到 `/api/health` 供观测（对齐既有「AI 缓存表孤儿导致磁盘膨胀」的教训）。
8. **缓存串号**：`notesCache` 属"按用户私有"，必须在 `core.js` 的 `bus.on('auth:changed')` 回调里与 `qaCache` 一同 `clear()`（换账号串笔记是必现事故）。

## 11. 决策定稿（原「待确认」四项 + 实现期新增决策）

### 11.1 原待确认项的落定

1. **一篇 vs 多篇** → 定稿「每视频多篇 + 可合并」。`user_notes` 不加 `(user_id, content_key)` 唯一约束；同视频笔记在 Tab 内以卡片流呈现，P1 提供「合并为一篇」与按时间线导出。
2. **B 站/YouTube 服务端取帧是否提前** → 定稿**提前到 P0**（`frames.py` 已实现）。三平台截图能力 P0 即一致：native 前端 Canvas 抓帧；B 站/YouTube 走 `POST /api/me/notes/frames`，**只查流播缓存**（复用 `main.py` 注入的 `_stream_cache_lookup`，未命中不触发整片下载），抽帧失败回退 yt-dlp 封面（`frame_type:"poster"`，前端提示「先完整播放一次可截到当前帧」）。**永不出死按钮**。
3. **笔记是否入合集** → 维持 P1。`collection_items` 保持视频粒度，笔记粒度入集与「合集详情页展示笔记摘要」一起做。
4. **匿名态** → 定稿「引导登录」。未登录点笔记 Tab 渲染面板内登录引导卡（复刻 `history.js` 的 `renderLoginPrompt` 风格 + `openAuth('login')`），不做 localStorage 本地草稿。

### 11.2 实现期新增/修正的关键决策

5. **独立 `backend/notes` 包**（定稿，理由见 §3）：library 是「归属与时间线」只记引用，笔记是「内容本体」存正文/图片/版本/冲突，上限与生命周期策略完全不同。两包只共享 `user_id` 列级隔离 + `content_key` 身份键两条约定；`library.service.KINDS` 加 `"note"` 完成徽标联动。
6. **SSRF 域名判定放过 fake-ip 段（`198.18.0.0/15`）**：`frames._is_private_host` 对**字面 IP** 全类别从严拒绝（private/loopback/link-local/reserved）；对**域名解析结果**改用显式内网网段清单 `_DOMAIN_BLOCKED_NETS` 判定，刻意不含 `198.18.0.0/15`——它是 Clash/Surge 等代理的 fake-ip 默认网段，Python 3.11+ 的 `is_private` 会将其判 True，而目标用户开代理访问 B 站/YouTube 是常态，误拒必现；该段不可路由到真实内部服务，DNS rebinding 场景下解析判定的增益本就有限，权衡后优先保可用性。
7. **`store._iso` 统一输出 naive UTC**：SQLite 存 `datetime` 丢 tzinfo，flush 期 ORM 对象带 `+00:00` 而回读不带，同一时刻会产出两种 ISO 串 → 前端 `base_updated_at` 冲突基线比对与展示不一致。定稿：所有出参时间统一 `astimezone(utc).replace(tzinfo=None)` 后 `isoformat()`。
8. **`create_note` 认领孤儿后必须回写 `image_count`**：新建未保存时贴的图（`note_id IS NULL` 孤儿行）在 `create_note` 里按 `content_key` 认领；认领后调用 `_touch_note_image_count` 回写冗余计数列，否则 `get_note` 读行仍是 0、列表徽标错误。
9. **前端播放器能力经 ctx 注入**：`playerCtrl` 是 `result.js` 模块级私有单例，`notes.js` 不直接 import；由 `loadNotes` 注入 `ctx = {contentKey, url, title, getCtrl, onPlayer, mountPlayer}` 桥接。TAB_LOADERS 签名统一为 `(url, panel, card)`。时间戳取值链：`getCtrl().getTime()` → 字幕 Tab 当前高亮行 `data-t` → 提示手动播放。
10. **自动保存冲突期暂停防抖**：收到 409 后 `markDirty` 不再排自动保存定时器（避免用户未二选一时被反复 409 轰炸），内联横幅提供「用我的版本覆盖」（以 server.updated_at 为新基线 PATCH）/「改用服务端版本」（载入 server 内容）。
